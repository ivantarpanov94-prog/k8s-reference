Cluster Architecture: Master vs. Worker

Master Node (Control Plane)

Role: Acts as the control center, managing overall operation and coordination of worker nodes.

Key Components:
  • etcd: Distributed key-value store maintaining all cluster data, state, and configuration.
  • Kube API Server: Central management interface facilitating all communication and operations.
  • Scheduler: Assigns pods to optimal nodes based on resources and constraints.
  • Controllers: Operational background workers ensuring desired state (e.g., replication, node availability).

Worker Node

Role: Responsible for running application containers and executing workloads assigned by the master node.

Key Components:
  • Kubelet: The "captain on ship"—manages container lifecycle and reports status back to Kube API Server.
  • Kube Proxy: Manages networking rules for seamless communication between containers and external traffic.
  • Container Runtime: Executes containers on host system (e.g., containerd, CRI-O, Docker).

Component Deep Dives

🔑 etcd Deep Dive

  • Role & Storage: Serves as the distributed key-value store for Kubernetes, holding all cluster state data, metadata, and configuration settings.
  • Architecture: Operates via etcd server and client interactions, ensuring high availability and consistent data replication across the control plane.
  • API Server Integration: The Kube API Server is the only component that communicates directly with etcd, connecting securely over TLS endpoints.
  • Cluster Deployment: Can run as a stacked static pod (e.g., kube-system) or as an external, dedicated etcd cluster. Default data directory is typically /var/lib/etcd.
  • Security: All communication must be encrypted using TLS certificates to guarantee data confidentiality and integrity.
  • Management Tool: Managed directly via the etcdctl command-line utility for snapshot backups, health checks, and key queries.

🌐 kube-apiserver Deep Dive

  • Primary Function: Orchestrates all operations within the Kubernetes cluster, acting as the central communication hub and entry point for all control plane and worker components.
  • API Access & Management: Serves as the target interface for kubectl CLI commands and automated REST calls, handling CRUD operations on cluster resources.
  • Data Interaction: Exclusively reads from and writes to etcd to persist cluster state changes, ensuring data consistency across the environment.
  • Architectural Hub: Coordinates communication across Kubelets, the Scheduler, Controller Manager, and external controllers.
  • Security Pipeline: Enforces security mechanisms on every request through three sequential gates: Authentication, Authorization (RBAC), and Admission Control.
  • Scaling & Performance: Designed to scale horizontally. Multiple instances run stateless behind a load balancer to handle high traffic demands and ensure high availability.
  • Versioning & Updates: Supports concurrent API versioning (e.g., v1, v1beta1) to allow smooth rolling upgrades and backward compatibility without service disruption.

⚙️ kube-controller-manager Deep Dive

  • Role in Kubernetes: Manages various background control loops (controllers) that continuously regulate and drive the actual state of the cluster to match the desired state.
  • Stateless State Management: Does not hold internal state or metadata; instead, it reads the intended state from etcd via the kube-apiserver and issues modifications to align the system.
  • Key Controller Functions:
    • Node Controller: Monitors node health via heartbeats, taking corrective action if nodes become unreachable.
    • Replication Controller: Maintains the exact requested count of pod replicas across the cluster.
    • Endpoints Controller: Populates Endpoints objects to link Kubernetes Services with corresponding target Pods.
    • Service Account & Token Controllers: Automates creation of default service accounts and API access tokens for new namespaces.
  • REST API Interaction: Communicates exclusively with the kube-apiserver using REST endpoints to watch cluster state changes and issue corrective API updates.
  • Leader Election: In multi-master High Availability setups, instances run in active-standby mode utilizing a leader election mechanism to ensure only one active manager drives decisions at a time.

⚙️ kube-scheduler Deep Dive

  • Role & Decision Maker: Serves as a vital control plane component that assigns unscheduled Pods to optimal Nodes in the cluster. *Note: It only decides placement—it does not physically run or create containers (handled by Kubelet).*
  • Two-Phase Scheduling Process:
    • 1. Filtering (Predicates): Eliminates nodes that fail resource capacity requirements (CPU/Memory) or constraint rules (Taints, Node Selectors).
    • 2. Ranking (Priorities): Scores and ranks remaining candidate nodes using priority functions to select the best target node with maximum available capacity.
  • Advanced Scheduling Constraints: Evaluates complex placement criteria including Resource Requests & Limits, Taints & Tolerations, Node Selectors, and Node/Pod Affinity & Anti-Affinity rules.
  • Customization & Multi-Scheduler: Supports custom scheduler configurations, custom plugins, or running multiple dedicated schedulers side-by-side in the same cluster.

🪖 Kubelet Deep Dive

  • Role & Primary Node Agent: Runs as an essential agent on every worker node in the cluster, responsible for managing the entire lifecycle of local Pods and containers.
  • Pod Specification (PodSpec) Execution: Continuously fetches PodSpec definitions from the kube-apiserver and takes corrective actions to ensure running container states strictly match desired specs.
  • Container Runtime Interface (CRI): Interacts directly with the underlying Container Runtime (e.g., containerd, CRI-O, Docker) to issue create, start, stop, and destroy commands.
  • Node Registration & Capacity Reporting: Registers host node details (CPU/Memory capacity, availability, labels) with the API server so the Scheduler can make informed placement decisions.
  • Health Monitoring & Probes: Executes periodic liveness, readiness, and startup health checks, reporting node and pod status metrics continuously back to the Master node.

🔀 Kube-Proxy Deep Dive

  • Role & Traffic Management: Runs as a network daemon on every worker node, maintaining packet routing and filtering rules to handle network traffic directed toward Kubernetes Services.
  • Service Abstraction & IP Stability: Solves ephemeral Pod IP changes by providing stable virtual IPs (ClusterIPs/NodePorts), dynamically mapping Service IPs to active backend Pod endpoints.
  • Traffic Forwarding Engines: Leverages host network packet filtering mechanisms—primarily iptables or high-performance IPVS—to load balance and route incoming requests automatically.
  • Continuous State Watching: Watches the kube-apiserver for Service and Endpoint/EndpointSlice creations or updates, keeping node networking rules synchronized in real time.
  • Scope Clarification: Manages routing to Services; it does not handle direct Pod-to-Pod overlay container networking (which is handled by the CNI plugin like Calico or Flannel).

📦 Pods Deep Dive

  • Smallest Deployable Unit: The foundational execution block in Kubernetes, encapsulating one or more tightly-coupled application containers.
  • Shared Network & Storage Namespace: Containers within the same Pod share a single network IP address and network stack, allowing them to communicate via localhost and share attached storage volumes.
  • Multi-Container Patterns: Supports running secondary sidecar/helper processes (e.g., log shippers, proxies) alongside primary application containers within a single Pod boundaries.
  • Ephemeral Lifecycle: Pods are non-permanent; Kubernetes continuously orchestrates their creation, destruction, scaling, and rescheduling based on target controller replicas.
  • Resource Limits & Scheduling: Defines precise CPU and Memory Requests (minimum guaranteed) and Limits (maximum allowed), driving informed scheduling choices by the kube-scheduler.
  • Health Monitoring: Monitored continuously by Kubelet through Liveness and Readiness probes to automatically restart failed containers or remove unready pods from Service routing.
